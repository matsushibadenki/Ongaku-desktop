# ADR-0003: 安定化優先とアプリ内の責務境界

- 状態: Accepted（Mobile受信commitとPlayback session storeは実装済み。Library query等は移行中）
- 決定日: 2026-09-05
- 根拠: [全体設計レビュー](../ARCHITECTURE_REVIEW_2026-09-05.md)
- ADR-0001、ADR-0002を補足する。具体的な着手順はROADMAPのみで管理する。

## 決定

ローカル音源の安全性と日常再生を最初の製品境界とする。MacのApple Music機能とMobile同期は能力・配布構成ごとに検証し、未検証の統合機能を完成範囲へ含めない。新規の共同編集、CloudKit、SharePlay、推薦拡張は保存・性能・配布のゲート通過後に扱う。

全面書き直しはせず、既存のテストを保持したまま、保存成功・検索結果・転送完了という観測可能な契約ごとに小さく移行する。

## 目標の責務

| 責務 | 所有するもの | 所有しないもの |
|---|---|---|
| Library domain | 安定ID、曲・プレイリスト・出所・能力、変更command | SwiftUI、MusicKit具体型、ファイルI/O |
| Catalog repository | 保存、移行、整合性、リビジョン、復旧 | 画面選択、通信、音声エンジン |
| Library query | 非同期検索、フィルタ、集計、索引差分、結果世代 | SwiftUIの描画、カタログの正本 |
| Playback session store | キュー、位置、イベントの高頻度保存と復旧 | 音源・書誌の全体保存 |
| Local playback / MusicKit adapter | 各再生経路と能力、排他的切り替え | 互換性のない音源の強制統一、DRM音声の抽出 |
| Transfer core / repository | メッセージ、検証、チェックポイント、受信commit、再送 | SwiftUI、端末の発見UI |
| Platform adapters | MCSession、権限、ファイル選択、出力機器、MusicKit API | 業務状態の複数の正本 |
| Presentation | MainActor上の表示状態、入力、進捗、エラー | 全件検索、ハッシュ計算、同期ディスクI/O |

最初は現行ターゲット内の型・protocolとして切り出す。Mac/Mobileで共有する純粋モデルと転送・保存契約が安定した段階で小さな共有Swift targetへ移す。レイヤーごとに大量のpackageを作らない。SPMだけでなくDeveloper ID、App Store、iOSのXcode構成も同じ変更でコンパイルする。

## 保存の契約

1. 永続化成功前に成功通知しない。転送のネットワーク上の受領とライブラリへのcommitは区別する。
2. 受信は転送ID、チェックサム、ライブラリIDで冪等性を管理する。commit後・ACK前に停止しても二重登録しない。
3. チェックポイントの削除は確定後の掃除であり、掃除失敗を音源保存失敗と混同しない。
4. 破損と空のライブラリを区別する。読み取れない正本を無条件に空データで上書きしない。
5. コピー先も検証する。原本参照のファイルは利用者が承認した操作範囲を越えて変更しない。
6. キューや履歴だけの更新で全曲カタログを書き直さない構成へ移行する。旧manifestからの一度限りの移行、バックアップ、再起動後の参照整合性を先に試験する。
7. 変更は保存側で直列化し、ライブラリID・リビジョンを照合する。await前の古い全配列を別の更新の上に書き戻さない。

## JSON / SQLite

現時点の正本はJSON、SQLiteは再生成可能な検索用モデル。ADR-0001の移行開始条件は既に成立しており、これ以上の保存負荷を機能追加で増やす前に対処する。

高頻度の再生キュー・履歴はライブラリUUID付きsidecarへ分離済み。検索のJSON fallbackもMainActor外へ分離済みで、残る索引全再生成を差分更新へ移す。SQLiteの正本化は、UUID、プレイリスト順、履歴参照、旧データ移行、途中終了、失敗復旧が検証された段階で別の判断として記録する。切替後に生じた更新を失う「古いJSONへ戻す」方式は復旧と呼ばない。最新状態のエクスポートまたは検証済みの逆移行を必要とする。

性能はReleaseで起動から表示、入力から結果、更新中の検索を計測し、再生保存との同時実行・ピークメモリ・書込量を含める。索引だけの数値をアプリ応答時間として表示しない。

## 開発と配布の契約

- 変更単位は再現条件→契約テスト→実装→関連構成ビルド→証拠記録。機械的なファイル分割を目的にしない。
- 純粋ロジック、repositoryの失敗注入、音声／MusicKit統合、署名UI、実機転送を別のゲートとして扱う。未実行を成功に含めない。
- 実装台帳の `[Done]` と配布可能の判定を分ける。現行リポジトリのパスと確認手順を伴わない機能を完了扱いしない。
- 新規UIと外部通信設定は英語・日本語・简体中文、キーボード、VoiceOver、意味の自然な改行を検証する。iPhoneはSafe Area、左右16pt、SE第3世代と16 Pro MaxのPreviewと実描画を確認する。
- Store権限は署名済みの実通信で最小構成を確認する。Developer ID版の合格をStore版の代用にしない。

## サーバー

現状はサーバーを追加しない。ローカル保存・再生・LAN同期の問題はアプリ内で解決する。将来、独立した共有サービスの必要性が確認できた場合はXServer VPS CloudのApp VPS + Managed PostgreSQL + NFSを中核候補とする。AI・バッチ等を通常VPSへ分離する際はHTTPS APIまたはジョブキュー経由とし、WorkerからManaged DBへの直接接続に依存しない。CloudKitとの責務重複も導入前に解消する。
