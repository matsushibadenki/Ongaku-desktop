# ADR-0001: 大規模ライブラリの保存方式とSQLite移行条件

- 状態: Accepted
- 決定日: 2026-08-17
- 対象: カタログスキーマ3以降

## 背景

現在のカタログは、原子的な置換、直前バックアップ、スキーマ移行を備えたJSON文書として保存している。構造が単純で、障害時に利用者と開発者が内容を確認しやすい一方、更新のたびに文書全体を書き直し、検索や集計は全件走査になる。

Ongaku Desktopは10万曲で初期表示2秒以内、一般検索300ms以内を目標とする。スマートプレイリスト、再生履歴、全文検索が加わると、JSONの全件デコードと全件走査がボトルネックになる可能性があるため、移行判断を感覚ではなく再現可能な計測に基づける。

## 決定

SQLite移行が完了するまではJSONカタログを正式な保存元として維持する。`LargeLibraryFixture`の決定論的な10万曲データをRelease構成で継続計測し、以下の移行条件を満たした時点でSQLiteへの段階移行を開始する。

### 標準fixture

- 100,000曲
- 5,000アーティスト
- 10,000アルバム
- 英語、日本語、简体中文を循環させた曲名
- 固定UUID、固定日時、固定パス、固定SHA-256相当値
- プレイリスト、再生イベント等の負荷は各機能の導入時に同じfixtureへ追加する

### 性能予算

| 操作 | Release構成のp95上限 |
|---|---:|
| JSONカタログのコールドロード | 2.0秒 |
| 曲名・アーティスト・アルバムの一般検索 | 300ms |
| アルバム／アーティストのグルーピング | 500ms |
| カタログ全体の原子的保存 | 1.5秒 |
| 計測中のピーク常駐メモリ | 512MiB |
| JSON manifestサイズ | 128MiB |

### 計測手順

1. 対象リリースと同じmacOS最小対応環境、および現行Apple silicon環境でReleaseビルドを使用する。
2. 他の高負荷処理を停止し、各操作をウォームアップ1回後に10回計測する。
3. 中央値とp95、ピーク常駐メモリ、manifestサイズをCI成果物へ保存する。
4. 次のコマンドでJSON保存、コールドロード、検索、グルーピングを測定する。

```sh
ONGAKU_RUN_LARGE_LIBRARY_BENCHMARK=1 swift test -c release --filter LargeLibraryPerformanceTests.catalogBenchmark
```

SQLiteプロトタイプの移行とFTS5検索は次のコマンドで測定する。

```sh
ONGAKU_RUN_SQLITE_CATALOG_BENCHMARK=1 swift test -c release --filter LargeLibraryPerformanceTests.sqliteCatalogBenchmark
```

### SQLite移行を開始する条件

次のいずれかを満たした場合、SQLite移行を`[Next]`へ昇格する。

1. 性能予算のいずれかを、同一基準環境の3回連続したRelease計測で超過する。
2. 10万曲での主要操作中に、メモリ圧迫、操作不能、原子的保存失敗のいずれかを再現する。
3. 全文検索、複合スマートプレイリスト、再生履歴集計が、全件走査では性能予算を守れない。
4. 25万曲、100万再生イベント、128MiB manifestのいずれかへ到達する。
5. 複数処理からの部分更新に、行単位トランザクションまたは索引が必要になる。

性能予算の80%へ到達した時点で警告とし、SQLiteプロトタイプと移行時間の計測を開始する。単発のDebug計測や一時的なCI遅延だけでは移行を決定しない。

## SQLite移行時の方針

- Apple標準SQLiteを基盤とし、WAL、外部キー、スキーママイグレーションを有効にする。
- `Library`、`Track`、`Artist`、`Album`、`Playlist`、`PlaylistEntry`、`PlaybackEvent`の既存UUIDを変更しない。
- JSONを読み取り専用スナップショットとして保持し、SQLiteへの取り込みを単一トランザクションで実行する。
- 件数、UUID集合、プレイリスト順序、イベント参照を検証してからSQLiteを正式な保存元へ切り替える。
- 少なくとも1リリースはJSONへ戻せるロールバック経路を維持する。
- 検索索引と履歴索引は実際のクエリ計画を計測して追加し、推測による過剰な索引を避ける。

## 初回判定結果

2026-08-17の開発環境でRelease計測を3回実施した。各行は10サンプルのp95である。

| 実行 | 保存 | コールドロード | 一般検索 | グルーピング | manifest |
|---:|---:|---:|---:|---:|---:|
| 1 | 1.379秒 | 0.683秒 | 0.380秒 | 0.034秒 | 61,487,930バイト |
| 2 | 1.431秒 | 0.690秒 | 0.394秒 | 0.030秒 | 61,487,930バイト |
| 3 | 1.454秒 | 0.726秒 | 0.375秒 | 0.091秒 | 61,487,930バイト |

一般検索が3回連続で300msを超えたため、SQLite移行開始条件1が成立した。原子的保存も性能予算の80%を超えている。したがって、索引付き検索を含むSQLiteプロトタイプとJSONからの検証可能な移行処理を次の実装対象へ昇格する。移行とロールバック検証が完了するまではJSONを正式な保存元として維持する。

## プロトタイプ結果

2026-08-17にApple標準SQLite、WAL、外部キー、FTS5を用いたプロトタイプを実装した。JSONスナップショットから単一トランザクションで移行し、全テーブルの件数・安定UUID、プレイリスト順序、外部キーを検証してからSQLiteファイルを確定する。移行失敗時はステージングDBを破棄し、明示的なロールバックでは検証済みJSONスナップショットを復元する。

初期の10万曲Release計測では、移行2.015秒、FTS5検索p95 0.475ms、SQLiteファイル63,406,080バイトだった。部分一致と英字の大小・アクセント・全角半角をJSON検索と揃えるため、正規化済み列とFTS5 trigram索引へ更新した後の再計測は、移行2.364秒、検索p95 0.555ms、SQLiteファイル77,119,488バイトだった。検索は300msの性能予算を大きく下回っている。

JSON／SQLiteのdual-readでは、全テーブルの件数・UUID・参照整合性に加え、曲名・アーティスト・アルバムに対する代表検索語の結果ID集合を比較する。一致したリビジョンだけアプリ内検索をSQLiteへ切り替え、ライブラリ更新ごとに索引を再生成して再検証する。同期中、検証不一致、SQLiteエラー時はJSONの線形検索を継続する。現段階ではJSONを正式な保存元として維持し、SQLiteは検証済みの検索用読み取りモデルとして扱う。

## 影響

- JSONの可読性と既存の復旧経路を当面維持できる。
- 大規模化による劣化を同じfixtureで比較できる。
- 検索や履歴機能の実装時には性能計測が必須になる。
- SQLite移行条件を満たした場合は、機能追加よりデータ移行とロールバック検証を優先する。
